# tanaoroshi-app — 画箋堂 棚卸PWA

スマホ(iPhone / **Android両対応**)・PCのブラウザで動く棚卸アプリ。
現行のiOS専用棚卸ツールを置き換え、ランニングコストゼロで運用することが目的。

- バーコード読取: スマホカメラ + ZXing(ローカルバンドル。CDN不使用)
- データ保存: 端末内 IndexedDB(オフラインでも棚卸作業を継続可能)
- 提出: GAS Webアプリ経由で Googleスプレッドシートに追記
- 商品マスタ: スプレッドシートで一元管理し、端末から手動同期(v1.2.0〜)。CSV直接取込も併存
- CSV: 商品マスタの取込(スマレジCSV対応・Shift_JIS自動判定) / 棚卸結果の出力

## GAS API(通信仕様)

全アクション共通: `POST` / `Content-Type: text/plain`(CORSプリフライト回避) / body はJSON文字列。
**先頭で必ず token を検証**(標準§3.5)。レスポンスは `{success:true, data}` | `{success:false, error}`。

| action | リクエスト | レスポンス data |
|---|---|---|
| `ping` | `{token, action}` | `{message}` |
| `submit` | `{token, action, session:{name,id}, staff, items:[…]}` | `{rows}` 追記した行数 |
| **`getProducts`** | `{token, action, offset, limit}` | `{items:[{jan,name,cost}], total, offset, count}` |

`getProducts` は**ページング必須**(設計判断#13)。呼び出し側は `offset` を `count` ずつ進め、
`offset + count >= total` になるまで繰り返す。`limit` の上限はGAS側で 5,000 に制限する。

## デプロイ手順

### 1. バックエンド(GAS)

1. Googleスプレッドシートを新規作成(例:「棚卸データ 2026」)
2. 拡張機能 → Apps Script → `gas/Code.gs` の内容を貼り付けて保存
3. スプレッドシートにシート `settings` を作成し、A1=`token`、B1=任意の長い英数字(例: 32文字)を入力
4. Apps Scriptで **`setupProductMaster()` を1回実行**(商品マスタシートを作成。下記「3. 商品マスタの一元管理」参照)
5. デプロイ → 新しいデプロイ → ウェブアプリ
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員** ← fetchで届かせるために必須。代わりにtoken認証で保護
6. 発行URL(`…/exec`)を控える

### 2. フロントエンド(PWA)

PWA(Service Worker・カメラ)は **HTTPS配信が必須**。無料で済む選択肢:

- **GitHub Pages(推奨)**: このフォルダをリポジトリにpushし、Settings → Pages で公開
- 社内で既にHTTPSの静的ホスティングがあればそこでも可

公開後、スマホのブラウザでURLを開き:
- iPhone: 共有 → 「ホーム画面に追加」
- Android: メニュー → 「アプリをインストール」

### 3. 商品マスタの一元管理(スプレッドシート側・v1.2.0〜)

商品マスタは**スプレッドシートで一元管理**し、各端末は「商品情報」タブの
**「☁️ スプレッドシートから同期」**ボタンで取り込む(設計判断#11)。

#### 3-1. シートの用意(初回のみ)

Apps Scriptで **`setupProductMaster()` を1回実行**する。シート `商品マスタ` が作られ、
**全体がプレーンテキスト書式**に設定される(JANの先頭ゼロ落ち・指数表記を防ぐ。標準§4-1)。

#### 3-2. マスタの更新(スマレジCSVを差し替えるたび)

1. スマレジから商品CSVをエクスポート
2. スプレッドシートで **シート `商品マスタ` を開いた状態**にする
3. **ファイル → インポート → アップロード** でCSVを選択
4. インポート場所: **「現在のシートを置き換える」**
5. 区切り文字: 自動検出
6. **「テキストを数値、日付、数式に変換する」は必ずオフ** ← オンだとJANが数値化され、
   先頭が0のコードでゼロが落ちる(標準§4-1)
7. インポート → 各端末で「☁️ スプレッドシートから同期」を押す

> **アプリからスプレッドシートへCSVを送る機能は無い**(意図的。スプレッドシート標準の
> インポート機能で足りるため、アプリに持たせない — 設計判断#11)

#### 3-3. シート構成(スマレジCSVをそのまま貼る)

**列を並べ替える必要はない。1行目の見出しでGASが列を探す**(設計判断#12)。

| 用途 | 見出しの候補(前方から部分一致で探索) | スマレジCSVでの位置 |
|---|---|---|
| JANコード | `商品コード` / `JAN` / `jan` / `バーコード` | **C列** |
| 商品名 | `商品名` / `品名` | **D列** |
| 原価 | `原価` / `仕入原価` / `仕入価格` / `仕入単価` | **H列** |

- G列「商品単価」は**売価**であり取り込まない。E列「オープン価格」は金額ではなく 0/1 のフラグ
- 見出しで探すため、**スマレジの出力列が増減しても壊れない**
- 見出しが見つからない場合、同期は「見出しが見つかりません」と**明示的に失敗**する
  (誤った列を黙って取り込まない)

### 4. 拠点(店舗)と棚卸データシート(v1.3.0〜)

複数拠点で使う。**スプレッドシートは1つ・商品マスタは全拠点共通**。棚卸の提出先だけ
**拠点ごとのシート**に自動で振り分ける(設計判断#16)。

| 拠点コード(内部) | 画面の表示名 | 提出先シート(自動作成) |
|---|---|---|
| GWH | 本店 | `棚卸データ_GWH` |
| GWS | 京都精華大学店 | `棚卸データ_GWS` |
| GWK | 京都美術工芸店 | `棚卸データ_GWK` |
| GWC | 京都市立芸術大学店 | `棚卸データ_GWC` |

- 端末の「設定」タブで**拠点を1つ選ぶ**。画面には**日本語の表示名**が出る(上表)。提出時にその拠点のシートへ追記される
- シートが無ければGASが**見出し・書式つきで自動作成**する(手作業のシート準備は不要)
- 拠点コードはGAS側の許可リストで検証する。**リストにないコードは提出を弾く**(誤ったシートの乱造防止)
- 拠点未選択の端末は従来どおり `棚卸データ`(サフィックス無し)に出る(移行期の後方互換)
- **表示名と内部コードは分離**(v1.3.1)。画面表示・トーストは日本語名、提出payload・シート名・
  設定リンクの `loc` は**コード(GWH等)のまま**。表示名は `app.js` の `LOCATIONS` の `label` を変えるだけ。
  拠点の追加時のみ `app.js` と `gas/Code.gs` の両方の `LOCATIONS` にコードを足す

### 5. 端末側の初期設定(各端末1回)

**方法A: 設定リンク(推奨・多台数向け)** — 設計判断#17

1. 管理者が自分の端末で「設定」タブに提出先URL・トークンを入力して保存
2. 同じ画面の**「配布用の設定リンクを作る」**で、拠点ごとのリンク(GWH/GWS/GWK/GWC)を生成
3. 拠点ごとに1つのリンク(またはそのQRコード)を各端末で開くだけで、
   **URL・トークン・拠点が自動入力**され初期設定が完了する
4. 各端末で「商品情報」→「☁️ スプレッドシートから同期」を1回押す

> **トークンはURLの `#`(フラグメント)に載せ、`?`(クエリ)には載せない**(設計判断#17)。
> フラグメントはサーバーへ送信されず、GitHub Pagesのアクセスログにトークンが残らない。
> 適用後はアプリが**アドレスバーからフラグメントを消す**(履歴・ブックマークへの残留を防ぐ)。
> それでも共有トークンをリンクで配る以上、**リンク自体は社内限りで扱う**こと。

**方法B: 手入力(1〜2台なら手軽)**

1. 「設定」タブ → 担当者名・提出先URL・トークンを入力し、**拠点を選ぶ** → 保存 → 接続テスト
2. 「商品情報」→「☁️ スプレッドシートから同期」

いずれの方法でも、通信できない場所では「📥 CSVから取り込む(予備)」でスマレジCSVを直接取込できる。

> **QRコードについて**: 現状アプリは設定リンクを**テキストで**生成する。QRにする場合は
> 社内のQR作成ツール・MDM・印刷機能で変換する。アプリ内でのQR画像生成は、CDN不使用の制約下で
> 正しく動くエンコーダを別途用意・検証してからにする方針(未実装。将来拡張の設計メモ参照)。

## 使い方(棚卸)

ホーム「📦 棚卸」→ 新規(名前を付ける) or 以前のデータに追加 → カメラ起動
→ 赤い線にバーコードを合わせる → 商品表示 → 数量入力 → 登録 → 自動でカメラに戻る
→ 終了したら「データ」タブから **Webへ提出**(スプレッドシート保存) or **CSV出力**

- 画面タップでズーム3段階、4回目で等倍に戻る
- ライトボタンは対応端末のみ表示(下記制約参照)
- 読み取れない場合は「読み取りをスキップして手入力」
- 同一商品を2回読んだ場合は注意表示の上、**加算行として追加**される(場所別に数える運用を想定)

## 既知の制約・設計判断ログ

| # | 事項 | 判断・理由 |
|---|---|---|
| 1 | **GAS HTML Serviceではなく静的PWA + GAS API構成**(標準§2の「google.script.run」から逸脱) | PWA(オフライン起動・ホーム画面追加・Service Worker)とカメラ連続読取はGASのサンドボックスiframeでは成立しないため。標準§9「プロジェクト内では設計書が正」に基づく明示的逸脱。費用ゼロは維持(GitHub Pages+GAS) |
| 2 | GASデプロイを「全員」アクセスにする | ドメイン限定にするとfetchがログインリダイレクトで失敗するため。代わりに settings シートの token で認証(§3.5の趣旨を担保) |
| 3 | 棚卸結果CSVは UTF-8(BOM付き) | ブラウザ標準ではShift_JISエンコード不可。Excelで開けることは確認済みの方式。スマレジ等がSJISを要求する場合はGAS側に変換出力を追加する(標準§4-8の方式) |
| 4 | iPhoneのライト(torch)ボタン | iOS Safariはtorch非対応の機種・OSが多く、対応検出できた場合のみボタン表示。非表示の場合はコントロールセンターのライト等で代替 |
| 5 | 同一JAN再スキャンは上書きでなく加算行 | 売場別・棚別に分けて数える現場運用を想定。合計はデータ確認画面とスプレッドシート側で集計 |
| 6 | 商品マスタの**実体**は端末ローカル(IndexedDB) | オフライン棚卸を成立させるため。読取時の照合は必ず端末内で完結させる。<br>~~端末ごとにCSV取込が必要~~ → **v1.2.0で `getProducts` 同期に拡張済み**(#11)。マスタの**正はスプレッドシート**になったが、実際に照合するのは端末内のコピーという構造は変えていない |
| 7 | 明細の即時保存 | 登録のたびIndexedDBへ書き込むため、アプリを閉じても・圏外でもデータは消えない(標準§3.7の趣旨) |
| 8 | **読取フォーマットは EAN_13 / EAN_8 のみ**(ITF・CODE_39・CODE_128 を無効化) | 棚卸対象はJAN商品のみでCODE系・ITFの読取運用が無いことを確認済み。ITFは既定でチェックデジット無し・6/8/10/12/14桁を許容するため、EAN-13の一部を短い桁数として**部分誤読**する。加えて多フォーマット総当たりはSafariで低速化を招く。JAN系に限定して誤読と低速を同時に解消(不具合ログ#2)。**棚札等でCODE_128を読む運用が将来生じたらモード別に限定有効化する** |
| 9 | **商品マスタの金額項目は「原価」**(v1.1.0で「売価」から変更) | 棚卸の目的は在庫金額を**原価ベース**で把握することのため。スマレジCSVは H列「原価」を取り込み、G列「商品単価」(売価)は取り込まない。<br>内部キーは `price` → `cost` に改称。ただし**旧データ(`price`)も読めるようフォールバック**する(`costOf()`)。既存端末に取込済みのマスタ・登録済み明細を無効にしないため、DBバージョンは上げず移行処理も行わない<br>GASへは `cost` と `price` の**両方のキーで送る**。`gas/Code.gs` を再デプロイしていない端末でも金額が欠落しないようにするための互換措置(再デプロイ後は `cost` が使われる) |
| 10 | **商品の個別登録は JAN・商品名を必須**(原価のみ任意) | 名称のない商品がマスタに入ると、棚卸時に「(名称なし)」としか出ず現場で判別できないため。<br>未入力の間は登録ボタンを**無効化**し、押下時のバリデーションも残す(二重の防御。IME確定前など入力イベントの取りこぼしに備える)<br>**スキャン中に現れた「マスタ外商品」の名称入力は従来どおり任意**。棚卸の手を止めないことを優先し、必須化はマスタ整備の画面に限定する |

| 11 | **商品マスタはスプレッドシートで一元管理し、端末は手動同期**(v1.2.0)<br>GASアクション `getProducts` / 認証は既存と同じ settings シートの token | 全端末に同じCSVを配って回る運用をやめるため。**正はスプレッドシート1か所**。<br>**同期は手動ボタンのみ**(自動同期なし)。棚卸中に勝手にマスタが変わって数え直しになるのを避ける。通信は棚卸の前後に限定でき、電波の悪い売場でも作業が止まらない<br>**アプリからスプレッドシートへCSVを送る機能は作らない**。スプレッドシート標準の「ファイル→インポート」で足りる。アプリに書き込み権限を持たせないほうが事故が少ない<br>**CSV直接取込は残す**。通信できない場所での初期セットアップと、GAS障害時のフォールバック手段として必要 |
| 12 | 商品マスタシートは**スマレジCSVをそのまま貼る**(列の並べ替えをさせない)。GASは**1行目の見出し名**で列を探す | 手作業の整形を挟むと更新が滞り、間違いも入るため。見出しで探せばスマレジの出力列が増減しても壊れない。<br>見出しが見つからないときは**エラーで止める**(位置決め打ちのフォールバックはしない)。誤った列を黙って取り込むと、原価に「税区分」が入るような**気づきにくい事故**になるため |
| 13 | 同期は**全ページ取得してから1トランザクションで置換**(取得しながら消さない) | 途中で通信が切れたときにマスタが空/虫食いのまま残ると、棚卸が始められなくなるため。<br>1回あたり **2,000件ずつ**取得する(GASの実行時間・レスポンスサイズ・モバイル回線を考慮)。進捗はローディング表示に出す |
| 14 | 同期は**全件置換**(差分更新をしない)。一方**CSV取込は追加・上書き**のまま変えない | 同期: スマレジ側で廃番になった商品が端末に残り続けるのを防ぐため。件数が数万件でも置換のほうが単純で、状態のズレが起きない<br>CSV取込: 予備手段であり「一部だけ足す」用途もあるため従来どおり。**廃番を消したいときは同期を使う**という使い分けを画面のヒントにも書いている |

| 15 | **GAS通信のエラー文言を利用者向けに統一**(v1.2.1)。`fetch`は共通関数 `gasPost()` に集約 | 店頭で使うのはIT専門でないスタッフのため、`Load failed`(Safari)・`Failed to fetch`(Chrome)といったブラウザ生の英語例外をそのまま出さない。<br>`gasPost()` が **通信断(TypeError)・タイムアウト・HTTP異常・非JSON応答・認証失敗**を日本語の対処つき文言に変換する。提出(`submit`)・接続テスト(`ping`)・マスタ同期(`getProducts`)の3経路が同じ関数を通る。<br>**提出の失敗時は必ず「データは端末に残っています」を添える**。データが消えたのではという不安を与えないため。<br>副次効果として、以前タイムアウトの無かった提出・接続テストにも60秒の打ち切りが入り、無応答で固まらなくなる |

| 16 | **拠点別の棚卸データシート**(v1.3.0)。1スプレッドシート・商品マスタ共通、棚卸データのみ `棚卸データ_<拠点>` に振り分け | GWH/GWS/GWK/GWC の4拠点・最大29台で運用するため。マスタは共通で二重管理を避け、集計だけ拠点別に分けたい。<br>提出時に端末の拠点をpayloadに載せ、GASが `棚卸データ_<拠点>` へ追記(無ければ見出し・書式つきで自動作成)。**拠点はGAS側の許可リストで検証**し、リスト外は弾く(不正な値でシートを乱造させない)。<br>**拠点未設定は従来の `棚卸データ` に出す**(既存データ・移行期の端末との後方互換)。拠点の追加はフロント/GAS両方の `LOCATIONS` にコードを足すだけ。<br>**表示名(日本語)と内部コードは分離**(v1.3.1)。画面・トーストは表示名、シート名・payload・設定リンクはコード。店舗名の変更が内部識別子やシート名に波及しないようにするため |
| 17 | **設定ディープリンクで初期設定を配布**(v1.3.0)。URL・トークン・拠点をリンクに埋め、開くだけで自動入力 | 最大29台に手入力で提出先URL・32桁トークン・拠点を設定して回るのは非現実的なため。拠点ごとに1リンク配ればよい。<br>**トークンは `#`(フラグメント)に載せ `?`(クエリ)に載せない**。フラグメントはHTTPリクエストに含まれずサーバーログに残らない(GitHub Pagesは静的配信でログにパスが残る)。<br>適用後は `history.replaceState` で**フラグメントを即座に除去**し、アドレスバー・履歴・ブックマークにトークンを残さない。<br>それでもリンクは共有シークレットを含むため**社内限りで配布**する運用前提。リンク生成はブラウザ内で完結し、**トークン・URLをリポジトリに書かない**(禁止事項の順守) |

### #2 カメラ読取がほぼ反応せず、読めても桁が欠ける（2026-07-23 修正）

| 項目 | 内容 |
|---|---|
| **症状** | JANのカメラ読取がほぼ反応しない。読めても数字の桁が一部欠けて「読込不良」になることが多く、完全に正しく読めるのは低確率。iPad Pro(第3世代)・iPhone 16 Pro いずれもSafariで同症状 |
| **切り分け** | 明るさ・距離・ズーム変更で改善せず、複数端末のSafari共通 → 環境要因でなく`scanner.js`の読取ロジックが原因と特定 |
| **原因** | `_buildReader` が読取対象に **ITF(Interleaved 2 of 5) と CODE_39** を含めていた。**ITFは既定でチェックデジット無し・許容長 `[6,8,10,12,14]`**（同梱バンドルの`ITFReader`で確認）のため、13桁EAN-13の縞の**一部を短い桁数のITFとして部分デコード**する＝「桁が欠ける」。またフォーマット5種×`TRY_HARDER`の総当たりがシングルスレッドのZXing(JS)には重く、iOS Safariの高解像度フレームで**デコード試行回数が落ちて「ほぼ反応しない」** |
| **なぜEANは桁欠けしないか** | EAN-13/8は構造固定＋チェックデジット検証があるため部分読取が通らない。よって桁欠け結果はITF/CODE_39由来と断定できた |
| **対策** | `POSSIBLE_FORMATS` を **`EAN_13` / `EAN_8` のみ**に限定（ITF・CODE_39・CODE_128 を除外）。誤読の解消と読取速度の改善に同時に効く。`zxing.min.js` は**無改変**（ヒント変更のみ＝CLAUDE.md「CDN置換・再ビルド禁止」に準拠）。`sw.js` の `CACHE_VERSION` を `v1.0.2` へ |
| **再発防止** | 検収手順書に回帰項目を追加：「桁欠け読取が発生しない」「JAN以外の桁数のバーコードに反応しない」「読取が速やかに反応する」 |
| **テストが検出できなかった理由** | 初回レビューは`scanner.js`の**フォーマット構成の妥当性まで踏み込まず**、実カメラ読取が実機必須のため見逃した。→ 読取フォーマットは「実運用で必要なものだけに限定する」を設計判断#8に明文化 |

**汎用化**: 「**ライブ動画のバーコード読取で ITF/CODE_39 を無闇に有効化すると、EANの部分誤読と低速化を招く。読取対象は実運用の記号系に限定する**」ほか、本件の教訓は**共通標準§4に反映済み**（v1.2 の落とし穴 **#16**「単発は成功するのに連続が失敗するならライブラリの連続デコード経路を疑う」・**#17**「仮説を実機検証せずに確定扱いしない／比較実験は変数を1つに」）。

#### #2 続報2：実機計測で「解像度不足」が確定 → 1080p化（2026-07-24）

**iPad Pro（第3世代）v1.0.3 実測値**

| 項目 | 実測 | 判断 |
|---|---|---|
| 解像度 | **720×1280** | **主因。** 短辺720pxでは小さいJANの1モジュールが1〜2pxに潰れ復号不能。要求した`ideal:1280×720`が縦向きで適用され短辺720になっていた |
| ピント(focusMode) | **API非対応** | iOSでは`focusMode`を制約制御できない。ただし**現物の映像は鮮明＝合焦済み**だったため、今回の犯人ではない → **施策1（連続AF）は不要と判断し不採用** |

| ライト / getCapabilities | あり / 対応 | ズーム・torchの制約制御は可能 |
| レンズ | 背面デュアル広角カメラ | 超広角/望遠の誤選択ではない |

| 項目 | 内容 |
|---|---|
| **対策(v1.0.4)** | カメラ制約を **`width:{ideal:1920}, height:{ideal:1080}`** へ引き上げ（短辺720→1080で1モジュールあたり画素が約1.5倍）。`min`は`OverconstrainedError`でカメラ起動自体が失敗し得るため**使わず`ideal`のみ**にする |
| **ズーム既定値** | **変更せず1×のまま。** 解像度単独の効果を切り分けるため、変更する変数を1つに絞る（一度に一つの原則）。高解像度化によりHWズームは初めて有効な手段になるので、1080pで不足なら次版で既定ズームを検討 |
| **診断パネル** | **継続表示**。v1.0.4適用後に「実際に1080p相当が返るか」を再計測して確認する |
| **段階的エスカレーション** | ①1080pで再計測・読取テスト → ②不足なら4K相当(`ideal:2560〜3840`)要求 → ③それでも極小ラベルが厳しければ赤線周辺のみ切り出してデコード(ROI) |

#### #2 続報3：1080p化でも改善せず → 解像度は主因でないと確定（2026-07-24）

**iPad Pro（第3世代）v1.0.4 実測**：`解像度 1080×1920`（720×1280から改善を確認）。
しかし**通常サイズのJAN（絵の具チューブ）でも読取は一切改善せず**。赤いガイド線に正しく合わせ、
写真で見てもピントは鮮明な状態で無反応。

→ **「解像度不足が主因」という診断は誤りだった**（v1.0.4の変更自体は無害なので維持）。
**カメラ実機を持たない状態で状況証拠から原因を絞る進め方を中止し、ZXingが実際に何を受け取り
何を返しているかを計測する方針に切り替える。**

**バンドル内部の確認結果**（`zxing.min.js`）
- `getCaptureCanvas()` は **canvasを一度だけ生成してキャッシュ**し、`createCaptureCanvas` は
  その時点の `videoWidth/videoHeight` で寸法を決める → **生成時に0だと0×0のまま固定**され、
  以後は空画像をデコードし続ける（`<video>`表示は独立なのでプレビューだけ正常に見える）
- ただし `decodeFromStream` は先頭で `this.reset()` を呼び、`canplay`/`playing` を待ってから
  再生を始める実装になっている → **上記は候補の一つであり断定はできない**

**v1.0.5（診断強化ビルド）で計測する5点**

| # | 計測値 | 判定できること |
|---|---|---|
| 1 | `video.videoWidth×videoHeight`・readyState | video要素が実際に持っている寸法（trackの1080×1920と一致するか） |
| 2 | **ZXingの`captureCanvas`実寸** | 0×0/極小なら**空画像をデコードし続けている＝原因確定** |
| 3 | **デコード試行回数/秒・成功回数** | 0ならデコードループ自体が回っていない |
| 4 | **例外の種類と内訳** | 従来 `if(!result) return;` で**捨てていた情報**。`Checksum`/`Format`例外が出ていればバーコードは検出できており画質/ROIの問題 |
| 5 | **📸フレーム取り込みテスト** | その瞬間のフレームを取り込み、**サムネイル表示＋平均輝度＋全画面デコード＋中央帯(ROI)デコード**。真っ黒/崩れなら取込経路の不具合、ROIだけ成功ならROI化が解 |

**あわせて**：読取成功後に `openConfirm`（IndexedDB等）で例外が出て**無反応に見える**可能性が
未排除のため、読取後の例外をトーストで可視化する（iOSでコンソールが見られないため）。

> **v1.0.5は計測専用**。読取ロジック（EAN限定・解像度・ズーム・重複抑制）は**一切変更しない**。

#### #2 続報4：単発は成功・連続は失敗 → 取り込み経路の問題と判明（2026-07-24 / v1.0.6で対策）

**v1.0.5 実機計測（iPad Pro第3世代）**
```
解像度(track): 1080×1920 30fps    video要素: 1080×1920 readyState=4
ZXing取込canvas: 1080×1920        デコード試行: 30回(15.3/秒) / 成功 0回
例外内訳: N:30 (NotFoundException)  読取後の例外: (なし)
```
これで **canvas 0×0／ループ停止／後段例外** の各仮説はすべて否定された。パイプラインは健全で、
**フレームの中身にバーコードを見つけられていない**状態。

**決定的な追加実測**

| 操作 | 結果 |
|---|---|
| 通常の連続スキャン | **ほぼ反応しない**（従来どおり） |
| **📸 単発フレーム取り込みテスト** | **高確率で読取成功**（ズーム×1でも×3〜4でも同様） |

同じカメラ・同じバーコードで**単発は成功し連続は失敗する**。よって
**「画素が足りない／ピントが悪い」は誤り**（前回までの診断を再度訂正）。差は**取り込み経路**にある。

**バンドル調査で判明した両経路の違い**

| | 連続（失敗） | 単発📸（成功） |
|---|---|---|
| 描画先 | ZXingの**キャッシュcanvas** | **毎回新規**canvas |
| コンテキスト | **`getContext("2d",{willReadFrequently:true})`** | `getContext("2d")`（既定） |
| デコード | 毎フレーム1回 | `decodeOnce`（リトライあり／静止画では結果は決定的） |

**機序（有力）**：`willReadFrequently:true` は canvas を**ソフトウェア（CPU）側**に置く指定。
iOSの動画フレームは**ハードウェアデコードでGPU側**にあり、この組み合わせでは
**転送に失敗して空／古い画素のまま**になることがある。canvasの*サイズ*は正常でも*中身*が空、
という今回の観測（サイズだけ確認して中身を見ていなかった盲点）と完全に整合する。

| 項目 | 内容 |
|---|---|
| **対策(v1.0.6)** | **ZXingの連続モード(`decodeFromConstraints`)の使用をやめ、自前スキャンループに置き換える**。各周回で「**既定コンテキストのcanvasへ`drawImage(video)`**」（＝実機で成功が実証済みの📸と同一経路）→ 低レベルAPI（`HTMLCanvasElementLuminanceSource`→`BinaryBitmap`/`HybridBinarizer`→`MultiFormatReader`）でデコード。周期200ms(5回/秒) |
| **誤検出対策** | **同一コードが2回連続で読めたときだけ確定**。「桁数が異なる読取」＝EAN_8の誤検出が実在すると判明したため |
| **機序の確定** | 📸テストを **A:既定canvas / B:`willReadFrequently:true` canvas** の**同一フレーム比較**に拡張。Bだけ真っ黒/デコード失敗なら機序が確定する |
| **不変** | カメラ取得条件(1080p・背面)・EAN限定・2秒重複抑制・ズーム/torch挙動・`zxing.min.js`無改変 |
| **リスク** | 読取ロジックの変更を伴うが、**置き換え先は実機で成功が実証済みの経路**。診断表示は残すため、改善しない場合も手がかりを確保できる |

#### #2 解決（v1.0.6）と、**原因は未確定**であることの記録（2026-07-24）

**実機結果（iPad Pro第3世代・iPhone 16 Pro / v1.0.6）— 解決**

| 確認項目 | 結果 |
|---|---|
| 通常スキャン | **劇的に改善**。赤線に合わせなくてもプレビュー内に入った瞬間に読み取る |
| 桁数間違い | 各種バーコードで**約20回テストして一度も発生せず**（2回連続一致の確定が有効） |
| 極小ラベル（鉛筆等） | **問題なし** |

**⚠️ ただし「なぜ直ったか」の機序は未確定**

対策時の有力仮説は「ZXingのキャプチャcanvasが `getContext('2d',{willReadFrequently:true})` で
作られており、iOSでGPU上の動画フレームを転送できていない」だった。
これを実機の📸A/B比較（同一フレームを A:既定canvas / B:willReadFrequently canvas に描画）で
検証した結果:

```
【A】既定canvas            : 平均輝度137  デコード ✅成功 4900669030799
【B】willReadFrequently    : 平均輝度144  デコード ✅成功 4900669030799
```
サムネイルも2枚ともバーコードが鮮明に写っていた。→ **仮説は否定された。**

**A/Bテスト自体の限界（設計上の欠陥）**：AもBも**新規作成したcanvas**で比較したため、
検証できたのは**コンテキストの種類のみ**。ZXing実装のもう一つの特徴である
「**canvasを1枚生成して使い回す**」点は**切り分けられていない**。

**これまでに除外できた要因（実測にもとづく）**

| 除外された要因 | 根拠 |
|---|---|
| 解像度不足・ピント不良・バーコードが小さい | 同一カメラの**単発取込では成功**。1080p化でも連続は改善せず |
| 取込canvasが 0×0（空画像） | 診断で `1080×1920` と正常 |
| デコードループが回っていない | `15.3回/秒` で稼働 |
| 読取後（`openConfirm`等）の例外で無反応 | 「読取後の例外: (なし)」 |
| **canvasのコンテキスト種別（willReadFrequently）** | **上記A/Bで両方成功＝否定** |
| 読取フォーマット設定・`zxing.min.js` の不具合 | 同じ設定で単発は成功する |

**残る候補（いずれも未検証）**：ZXingの `decodeFromConstraints` 連続経路の内部挙動
—— 使い回しcanvasの内容がiOSで更新されない（陳腐化）、内部スケジューリングや
`decodeWithState` のキャッシュ状態、ZXingが用意するvideo要素の扱い、など。

**確実に言えること**：ZXing内蔵の連続デコードをやめ、**毎周回 明示的に `drawImage(video)` して
低レベルAPIでデコードする自前ループに置き換えたら解決した**。原因の断定は行わない。

**診断UIの撤去（v1.0.7）**：計測は役目を終えたため、📷診断パネル・📸フレーム取り込みテスト・
🔄更新ボタン・サムネイル・統計収集を撤去。**復元が必要なら `46e4c17`(v1.0.5) /
`6fa5fe1`(v1.0.6) / `63e8d35`(v1.0.6.1) から戻せる**。
なお**読取後の例外をトーストで表示する処理は残す**（診断ではなく、
「読取は成功したのに後段のエラーで無反応」を防ぐ安全網のため）。

# tanaoroshi-app — 画箋堂 棚卸PWA

スマホ(iPhone / **Android両対応**)・PCのブラウザで動く棚卸アプリ。
現行のiOS専用棚卸ツールを置き換え、ランニングコストゼロで運用することが目的。

- バーコード読取: スマホカメラ + ZXing(ローカルバンドル。CDN不使用)
- データ保存: 端末内 IndexedDB(オフラインでも棚卸作業を継続可能)
- 提出: GAS Webアプリ経由で Googleスプレッドシートに追記
- CSV: 商品マスタの取込(スマレジCSV対応・Shift_JIS自動判定) / 棚卸結果の出力

## デプロイ手順

### 1. バックエンド(GAS)

1. Googleスプレッドシートを新規作成(例:「棚卸データ 2026」)
2. 拡張機能 → Apps Script → `gas/Code.gs` の内容を貼り付けて保存
3. スプレッドシートにシート `settings` を作成し、A1=`token`、B1=任意の長い英数字(例: 32文字)を入力
4. デプロイ → 新しいデプロイ → ウェブアプリ
   - 次のユーザーとして実行: **自分**
   - アクセスできるユーザー: **全員** ← fetchで届かせるために必須。代わりにtoken認証で保護
5. 発行URL(`…/exec`)を控える

### 2. フロントエンド(PWA)

PWA(Service Worker・カメラ)は **HTTPS配信が必須**。無料で済む選択肢:

- **GitHub Pages(推奨)**: このフォルダをリポジトリにpushし、Settings → Pages で公開
- 社内で既にHTTPSの静的ホスティングがあればそこでも可

公開後、スマホのブラウザでURLを開き:
- iPhone: 共有 → 「ホーム画面に追加」
- Android: メニュー → 「アプリをインストール」

### 3. 端末側の初期設定(各端末1回)

1. 「設定」タブ → 担当者名・提出先URL・トークンを入力 → 保存 → 接続テスト
2. 「商品情報」タブ → スマレジからエクスポートした商品CSVを取り込む
   (列の対応は自動推定。画面で確認して取込)

## 使い方(棚卸)

ホーム「📦 棚卸」→ 新規(名前を付ける) or 以前のデータに追加 → カメラ起動
→ 赤い線にバーコードを合わせる → 商品表示 → 数量入力 → 登録 → 自動でカメラに戻る
→ 終了したら「データ」タブから **Webへ提出**(スプレッドシート保存) or **CSV出力**

- 画面タップでズーム3段階、4回目で等倍に戻る
- ライトボタンは対応端末のみ表示(下記制約参照)
- 読み取れない場合は「読み取りをスキップして手入力」
- 同一商品を2回読んだ場合は注意表示の上、**加算行として追加**される(場所別に数える運用を想定)

| # | 事項 | 判断・理由 |
|---|---|---|
| 1 | **GAS HTML Serviceではなく静的PWA + GAS API構成**(標準§2の「google.script.run」から逸脱) | PWA(オフライン起動・ホーム画面追加・Service Worker)とカメラ連続読取はGASのサンドボックスiframeでは成立しないため。標準§9「プロジェクト内では設計書が正」に基づく明示的逸脱。費用ゼロは維持(GitHub Pages+GAS) |
| 2 | GASデプロイを「全員」アクセスにする | ドメイン限定にするとfetchがログインリダイレクトで失敗するため。代わりに settings シートの token で認証(§3.5の趣旨を担保) |
| 3 | 棚卸結果CSVは UTF-8(BOM付き) | ブラウザ標準ではShift_JISエンコード不可。Excelで開けることは確認済みの方式。スマレジ等がSJISを要求する場合はGAS側に変換出力を追加する(標準§4-8の方式) |
| 4 | iPhoneのライト(torch)ボタン | iOS Safariはtorch非対応の機種・OSが多く、対応検出できた場合のみボタン表示。非表示の場合はコントロールセンターのライト等で代替 |
| 5 | 同一JAN再スキャンは上書きでなく加算行 | 売場別・棚別に分けて数える現場運用を想定。合計はデータ確認画面とスプレッドシート側で集計 |
| 6 | 商品マスタは端末ローカル(IndexedDB) | オフライン棚卸を成立させるため。端末ごとにCSV取込が必要。将来はGASの`getProducts`アクションで一括同期に拡張可 |
| 7 | 明細の即時保存 | 登録のたびIndexedDBへ書き込むため、アプリを閉じても・圏外でもデータは消えない(標準§3.7の趣旨) |
| 8 | **読取フォーマットは EAN_13 / EAN_8 のみ**(ITF・CODE_39・CODE_128 を無効化) | 棚卸対象はJAN商品のみでCODE系・ITFの読取運用が無いことを確認済み。ITFは既定でチェックデジット無し・6/8/10/12/14桁を許容するため、EAN-13の一部を短い桁数として**部分誤読**する。加えて多フォーマット総当たりはSafariで低速化を招く。JAN系に限定して誤読と低速を同時に解消(不具合ログ#2)。**棚札等でCODE_128を読む運用が将来生じたらモード別に限定有効化する** |

## 将来拡張(モード追加)の設計メモ

ホームのモードタイルは既に6モード分を配置済み(棚卸以外はdisabled)。
追加時は `index.html` にビューを追加し、`app.js` の `VIEW_TITLES` / `TAB_OF_VIEW` / `goto()` に登録する。
スキャン→商品表示の共通部品(`scanner.js` / `openConfirm`)は各モードで再利用できる構造。
データベース移行(スプレッドシート→DB)時は `submitToWeb()` の送信先と `gas/Code.gs` のみ差し替えれば良い。

### #1 起動直後にローディングが出たまま操作不能 / ライトボタンが常時表示（2026-07-14 修正）

| 項目 | 内容 |
|---|---|
| **症状** | GitHub Pages公開後、アプリを開くとホームのモードタイルが薄く表示され、画面中央に「処理中…」が出たまま先に進めない。Chrome(通常/シークレット)・iPhoneいずれでも再現。DevToolsで IndexedDB が「No indexedDB detected」 |
| **原因** | CSSのカスケードで、**著者スタイルの `display` 指定がブラウザUAスタイルシートの `[hidden]{display:none}` を上書き**していた。`.spinner-overlay{display:flex}` により `<div id="spinner" hidden>` が常時表示となり、`position:fixed; inset:0; z-index:60` で全画面を覆って**全クリックを遮断**。背景 `rgba(247,245,240,.85)` が背後のタイルを薄く見せていた |
| **併発** | `#btn-torch` も `.big-btn{display:flex}` で同じ状態になり、**torch非対応端末でもライトボタンが常時表示**されていた（設計判断#4「対応検出できた場合のみボタン表示」への違反） |
| **誤診しやすい点** | ①「No indexedDB detected」は**原因でなく症状**。`dbOpen()` は遅延生成で、ホーム画面ではDB関数を呼ばないため、操作不能＝DBが永久に作られない。②Consoleの `A listener indicated an asynchronous response…` は**ブラウザ拡張由来のノイズ**で無関係 |
| **対策** | `css/style.css` に `[hidden]{display:none !important;}` を追加。`[hidden]` と `.big-btn` は詳細度が同じ(0,1,0)で記述順に依存するため、順序非依存にするため `!important` を付与。あわせて `sw.js` の `CACHE_VERSION` を `v1.0.1` へ（旧CSSがキャッシュ配信されると修正が届かないため必須） |
| **再発防止** | 検収手順書に回帰項目を追加：「起動直後にローディングが出ていない／ホームのタイルが押せる」「torch非対応端末でライトボタンが表示されない」 |
| **テストが検出できなかった理由** | コードレビューがJSロジック（`btn-torch.hidden = !torchSupported`）だけを設計書と突合し、**CSSとの相互作用を検証していなかった**。また実機なし検証でUIクリックが効かなかった際、原因を追わずJS直接実行でUI層を迂回したため見逃した。→ 以後、`hidden` 属性で制御する要素は**computed style での確認**を検証手順に含める |

**汎用化**: 他プロジェクトでも踏む落とし穴のため、**共通標準§4に反映済み**（`claude_app/00_GAS業務アプリ開発標準.md` v1.1 の落とし穴**#14**「`hidden` 属性は著者CSSの `display` に負ける」・**#15**「操作不能系の誤診パターン」）。

### #2 カメラ読取がほぼ反応せず、読めても桁が欠ける（2026-07-23 修正）

| 項目 | 内容 |
|---|---|
| **症状** | JANのカメラ読取がほぼ反応しない。読めても数字の桁が一部欠けて「読込不良」になることが多く、完全に正しく読めるのは低確率。iPad Pro(第3世代)・iPhone 16 Pro いずれもSafariで同症状 |
| **切り分け** | 明るさ・距離・ズーム変更で改善せず、複数端末のSafari共通 → 環境要因でなく`scanner.js`の読取ロジックが原因と特定 |
| **原因** | `_buildReader` が読取対象に **ITF(Interleaved 2 of 5) と CODE_39** を含めていた。**ITFは既定でチェックデジット無し・許容長 `[6,8,10,12,14]`**（同梱バンドルの`ITFReader`で確認）のため、13桁EAN-13の縞の**一部を短い桁数のITFとして部分デコード**する＝「桁が欠ける」。またフォーマット5種×`TRY_HARDER`の総当たりがシングルスレッドのZXing(JS)には重く、iOS Safariの高解像度フレームで**デコード試行回数が落ちて「ほぼ反応しない」** |
| **なぜEANは桁欠けしないか** | EAN-13/8は構造固定＋チェックデジット検証があるため部分読取が通らない。よって桁欠け結果はITF/CODE_39由来と断定できた |
| **対策** | `POSSIBLE_FORMATS` を **`EAN_13` / `EAN_8` のみ**に限定（ITF・CODE_39・CODE_128 を除外）。誤読の解消と読取速度の改善に同時に効く。`zxing.min.js` は**無改変**（ヒント変更のみ＝CLAUDE.md「CDN置換・再ビルド禁止」に準拠）。`sw.js` の `CACHE_VERSION` を `v1.0.2` へ |
| **再発防止** | 検収手順書に回帰項目を追加：「桁欠け読取が発生しない」「JAN以外の桁数のバーコードに反応しない」「読取が速やかに反応する」 |
| **テストが検出できなかった理由** | 初回レビューは`scanner.js`の**フォーマット構成の妥当性まで踏み込まず**、実カメラ読取が実機必須のため見逃した。→ 読取フォーマットは「実運用で必要なものだけに限定する」を設計判断#8に明文化 |

**汎用化候補**: 「**ライブ動画のバーコード読取で ITF/CODE_39 を無闇に有効化すると、EANの部分誤読と低速化を招く。読取対象は実運用の記号系に限定する**」は他プロジェクトでも有用。共通標準§4への追記を推奨（本コミット時点で**未反映**）。

#### #2 続報2：実機計測で「解像度不足」が確定 → 1080p化（2026-07-24）

**iPad Pro（第3世代）v1.0.3 実測値**

| 項目 | 実測 | 判断 |
|---|---|---|
| 解像度 | **720×1280** | **主因。** 短辺720pxでは小さいJANの1モジュールが1〜2pxに潰れ復号不能。要求した`ideal:1280×720`が縦向きで適用され短辺720になっていた |
| ピント(focusMode) | **API非対応** | iOSでは`focusMode`を制約制御できない。ただし**現物の映像は鮮明＝合焦済み**だったため、今回の犯人ではない → **施策1（連続AF）は不要と判断し不採用** |
| ズーム | 0.5〜10（現1） | HWズームは使えるが**デジタルズーム（クロップ拡大）**。低解像度では実画素が増えないため無効 |
| ライト / getCapabilities | あり / 対応 | ズーム・torchの制約制御は可能 |
| レンズ | 背面デュアル広角カメラ | 超広角/望遠の誤選択ではない |

**決め手**：「肉眼でくっきり見えるのに読めない」＋「**タップでズームしても改善しない**」。
デジタルズームは低解像度フレームを拡大するだけで実画素が増えないため、**土台の撮影解像度が不足している**ことの直接証拠になった。

| 項目 | 内容 |
|---|---|
| **対策(v1.0.4)** | カメラ制約を **`width:{ideal:1920}, height:{ideal:1080}`** へ引き上げ（短辺720→1080で1モジュールあたり画素が約1.5倍）。`min`は`OverconstrainedError`でカメラ起動自体が失敗し得るため**使わず`ideal`のみ**にする |
| **ズーム既定値** | **変更せず1×のまま。** 解像度単独の効果を切り分けるため、変更する変数を1つに絞る（一度に一つの原則）。高解像度化によりHWズームは初めて有効な手段になるので、1080pで不足なら次版で既定ズームを検討 |
| **診断パネル** | **継続表示**。v1.0.4適用後に「実際に1080p相当が返るか」を再計測して確認する |
| **段階的エスカレーション** | ①1080pで再計測・読取テスト → ②不足なら4K相当(`ideal:2560〜3840`)要求 → ③それでも極小ラベルが厳しければ赤線周辺のみ切り出してデコード(ROI) |

#### #2 続報3：1080p化でも改善せず → 解像度は主因でないと確定（2026-07-24）

**iPad Pro（第3世代）v1.0.4 実測**：`解像度 1080×1920`（720×1280から改善を確認）。
しかし**通常サイズのJAN（絵の具チューブ）でも読取は一切改善せず**。赤いガイド線に正しく合わせ、
写真で見てもピントは鮮明な状態で無反応。

→ **「解像度不足が主因」という診断は誤りだった**（v1.0.4の変更自体は無害なので維持）。
**カメラ実機を持たない状態で状況証拠から原因を絞る進め方を中止し、ZXingが実際に何を受け取り
何を返しているかを計測する方針に切り替える。**

**バンドル内部の確認結果**（`zxing.min.js`）
- `getCaptureCanvas()` は **canvasを一度だけ生成してキャッシュ**し、`createCaptureCanvas` は
  その時点の `videoWidth/videoHeight` で寸法を決める → **生成時に0だと0×0のまま固定**され、
  以後は空画像をデコードし続ける（`<video>`表示は独立なのでプレビューだけ正常に見える）
- ただし `decodeFromStream` は先頭で `this.reset()` を呼び、`canplay`/`playing` を待ってから
  再生を始める実装になっている → **上記は候補の一つであり断定はできない**

**v1.0.5（診断強化ビルド）で計測する5点**

| # | 計測値 | 判定できること |
|---|---|---|
| 1 | `video.videoWidth×videoHeight`・readyState | video要素が実際に持っている寸法（trackの1080×1920と一致するか） |
| 2 | **ZXingの`captureCanvas`実寸** | 0×0/極小なら**空画像をデコードし続けている＝原因確定** |
| 3 | **デコード試行回数/秒・成功回数** | 0ならデコードループ自体が回っていない |
| 4 | **例外の種類と内訳** | 従来 `if(!result) return;` で**捨てていた情報**。`Checksum`/`Format`例外が出ていればバーコードは検出できており画質/ROIの問題 |
| 5 | **📸フレーム取り込みテスト** | その瞬間のフレームを取り込み、**サムネイル表示＋平均輝度＋全画面デコード＋中央帯(ROI)デコード**。真っ黒/崩れなら取込経路の不具合、ROIだけ成功ならROI化が解 |

**あわせて**：読取成功後に `openConfirm`（IndexedDB等）で例外が出て**無反応に見える**可能性が
未排除のため、読取後の例外をトーストで可視化する（iOSでコンソールが見られないため）。

> **v1.0.5は計測専用**。読取ロジック（EAN限定・解像度・ズーム・重複抑制）は**一切変更しない**。

#### #2 続報4：単発は成功・連続は失敗 → 取り込み経路の問題と判明（2026-07-24 / v1.0.6で対策）

**v1.0.5 実機計測（iPad Pro第3世代）**
```
解像度(track): 1080×1920 30fps    video要素: 1080×1920 readyState=4
ZXing取込canvas: 1080×1920        デコード試行: 30回(15.3/秒) / 成功 0回
例外内訳: N:30 (NotFoundException)  読取後の例外: (なし)
```
これで **canvas 0×0／ループ停止／後段例外** の各仮説はすべて否定された。パイプラインは健全で、
**フレームの中身にバーコードを見つけられていない**状態。

**決定的な追加実測**

| 操作 | 結果 |
|---|---|
| 通常の連続スキャン | **ほぼ反応しない**（従来どおり） |
| **📸 単発フレーム取り込みテスト** | **高確率で読取成功**（ズーム×1でも×3〜4でも同様） |

同じカメラ・同じバーコードで**単発は成功し連続は失敗する**。よって
**「画素が足りない／ピントが悪い」は誤り**（前回までの診断を再度訂正）。差は**取り込み経路**にある。

**バンドル調査で判明した両経路の違い**

| | 連続（失敗） | 単発📸（成功） |
|---|---|---|
| 描画先 | ZXingの**キャッシュcanvas** | **毎回新規**canvas |
| コンテキスト | **`getContext("2d",{willReadFrequently:true})`** | `getContext("2d")`（既定） |
| デコード | 毎フレーム1回 | `decodeOnce`（リトライあり／静止画では結果は決定的） |

**機序（有力）**：`willReadFrequently:true` は canvas を**ソフトウェア（CPU）側**に置く指定。
iOSの動画フレームは**ハードウェアデコードでGPU側**にあり、この組み合わせでは
**転送に失敗して空／古い画素のまま**になることがある。canvasの*サイズ*は正常でも*中身*が空、
という今回の観測（サイズだけ確認して中身を見ていなかった盲点）と完全に整合する。

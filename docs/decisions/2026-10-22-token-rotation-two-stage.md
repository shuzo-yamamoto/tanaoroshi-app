# 端末を使っていない期間に、トークンの切り替えを2段階に分ける

## 背景
- 2026年10月の棚卸は終わり、どの端末も同期・提出をしていない。次の棚卸は2027年9月の予定。
- オーナーの提案（2026-10-22）は、次の2段階で進めること。
  - 段階1：管理者だけで、手順書 ⓪-13 の A〜C（トークンの生成 → 設定リンク・QR・印刷用PDFの作り直し → `settings` シートの書き換え）を近日中に行う。
  - 段階2：各端末の再設定（D）は、次の棚卸の前日に行う。運用ルールの「前日までに同期」と同じタイミングにする。
  - 段階1から段階2までの間、古いトークンの端末は「認証に失敗しました」になるが、使う予定が無い。
- 確認を求められた点：①未提出の棚卸が残っていても、再設定の後に提出できるか ②前日に再設定と同期をまとめて行う手順と、店舗の管理者向けの案内 ③未提出の確認を、全端末を見て回らずにスプレッドシート側でできるか。

## 決定内容
- **2段階で進めてよい**（README 設計判断#35、検収手順書 ⓪-13「端末を使っていない期間に切り替える場合（2段階）」）。
  - **漏れたトークンを早く無効にできる**（不具合ログ#6）。
  - 店舗の作業は、次の棚卸の前日の1回で済む。
- **① 未提出の棚卸**: 再設定の後に提出できることは、以前の検証で確かめてある。
  - 2026-10-20「切り替えの再現」（設定リンクを開いて再設定）。
  - ⓪-14（貼り付けで再設定）。
  - ただし、**約11か月使わない間に端末のデータが残り続けるかは確かめていない**。また、前年の棚卸を約1年後に提出すると、その時点の日時で今年のシートに追記され、集計が紛らわしい。そのため、**未提出は段階1の切り替え（C）の前に、古いトークンのうちに提出し終える**（S1-2）。段階2で前年の未提出が見つかったら、提出せずに管理者に相談する（S2-6）。
- **② 段階2の手順**: 次の順に行う（S2-1〜S2-6）。
  - 1週間ほど前：管理者がPCで接続テストをし、必要なら印刷用PDFを作り直して配る。
  - 前日：店舗へ連絡し、同期は店舗ごとに時間をずらす。
  - 各端末：版を確認（2回開き直し）→ 再設定（Android は N-3、iPhone・iPad は N-4）→ 接続テスト → クリップボードの上書き → 同期。
  - 店舗の管理者向けに、配る文面の例を手順書に入れた。
- **③ スプレッドシート側の確認**: スプレッドシートで分かるのは「提出された棚卸」だけで、未提出の棚卸は端末の中にしか無い。
  - 拠点ごとのシートを、棚卸名・担当者ごとに「行数・最初と最後の提出日時」でまとめる。管理者のブラウザで読み取り専用の `gviz/tq` のURLを使う（シートは変わらない）。同じ内容は QUERY 式でも見られる。
  - 店舗の管理者が「数えた棚卸がすべてあるか」を見比べ、足りない店舗だけ端末を確かめる。
- 段階1の新しいQR入り印刷用PDFは**掲示せず**、管理者のPCに保管する。店頭の古いQR入り印刷物は段階1で回収する。PCのアプリの設定は残しておく（段階2の前にリンク・QR・PDFを作り直すため）。
- コードの変更なし。

## 却下した案とその理由
- **未提出の棚卸を段階2まで持ち越し、再設定の後に提出する** … 長期間使わない端末のデータが残ることを確かめていない（端末の入れ替え・初期化・iOSの保存領域の扱い）。前年の棚卸が今年のシートに今年の日時で追記され、集計が紛らわしい。
- **段階1で新しいQR入りPDFを掲示する** … トークン入りの印刷物が、使わない期間ずっと店頭にあることになる。
- **未提出の確認をスプレッドシートだけで完結させる** … 未提出の棚卸はスプレッドシートに無いので、原理的にできない。提出済みの一覧と、各店舗の「数えた棚卸」を見比べる形にした。
- **アプリの一覧に「提出後に追加あり」を出す** … 現状は、提出した後に読み取りを追加しても「提出済」が消えない（`dbAddItem` が `submittedAt` を残す）。表示の改善は仕様外の機能追加なので、提案に留めた。今回は、行数の少ない棚卸を端末の明細の数と見比べる注意書きで対応する。

# iPhone・iPadのSafariから、ホーム画面のアプリへ設定リンクを渡す（案D）・トークン欄の伏せ字（v1.5.3）

## 背景
- v1.5.2 で「設定リンクを貼り付けて適用」欄を追加した（2026-10-20 の判断記録）。2026-10-21 のユーザーの実機確認の結果は次のとおり。
  - **Android**（機種名は未記入）は、QRを読むだけでホーム画面のアプリにも設定が入った。別の店舗のQRを読んで開き直すと拠点が切り替わった。テスト後に元へ戻した。
  - **iPhone 16 Pro** は、カメラでQRを写すと黄色の表示は出るが、長押ししてもメニューが出ず、**開かずにリンクをコピーできなかった**。v1.5.2 の手順書で推奨していた渡し方（掲示のQRからコピー）は使えない。
- iPhoneへの渡し方として、次の案を比較した（README 設計判断#32）。
  - 案A：アイコンを削除してQRで設定し、ホーム画面に追加し直す。
  - 案B：社内チャットの1対1・AirDrop。
  - 案C：アプリのカメラで設定QRを読む。
  - 案D：Safariで開いた画面から1回だけコピーする。
- 2026-10-21 オーナー指示: **案Dで進める**。案Bは予備として手順書に残し、案A・案Cは見送る。iPadのSafariでもボタンを出し（iPadはMacとして振る舞うことがあるので判定に注意）、iPadの検証項目も入れる。押した後に、ホーム画面のアプリで貼り付ける案内を画面に出す。
- あわせて、前回承認済みの2点を行う。
  - 「提出用トークン」欄を伏せ字にし、「表示」で見せる。画面の移動やアプリが裏に回ったら伏せ字に戻す。手順 M-2 は「表示してからコピー」にする。
  - 操作ガイドの6ページ目を見直し、印刷用PDF（QR画像入り）を作り直す。ページ数とQRが4枠に入ったことだけを確かめる。画面の撮影はせず、gitには入れない。

## 決定内容
- **案D**: 設定リンクで開いたとき、iPhone・iPad（iPod含む）のブラウザで、ホーム画面のアプリとして開いていなければ、設定画面のいちばん上に案内と「📋 ホーム画面のアプリ用に設定リンクをコピー」を出す。
  - 押すと、リンクをクリップボードへ入れる。予備として一時的な欄でのコピーも使う。
  - 押した後はボタンを消し、「コピーしました。ホーム画面のアプリを開き、『設定』→『📋 設定リンクを貼り付けて設定する』に貼り付けてください」と出す。
  - 受け取ったホーム画面のアプリ側は、v1.5.2 の貼り付け欄で適用する。
- **リンクの持ち方**: メモリ（`pendingSetupLink`）にだけ持ち、保存しない。アドレスバーからは従来どおりすぐ消す。
  - 捨てるのは、コピーした時点・設定画面を離れた時点・アプリが裏に回った時点。
  - 捨てた後に押すと「もう一度、店舗のQRコードを読み取ってから押してください。」と出す。
  - コピーに失敗したときは、リンクを保持してもう一度押せるようにする。
- **判定**（`isAppleMobileBrowser()`）:
  - UAに `iPhone|iPad|iPod` があるとき。または、`navigator.platform === 'MacIntel'` かつ `navigator.maxTouchPoints > 1` のとき（iPadのSafariの既定の「デスクトップ用Webサイト」表示。Macはタッチ点数0）。
  - `navigator.standalone === true` または `display-mode: standalone` のときは出さない（ホーム画面のアプリ）。
  - Android・PCには出さない。
- **トークン欄**（README 設計判断#33）:
  - ふだんは伏せ字（`-webkit-text-security`）。横の「表示」で平文にし、もう一度押すと伏せ字（ボタンの文字は「隠す」）。
  - 画面の移動・設定画面の開き直し・アプリが裏に回ったときに伏せ字へ戻す。
  - `type="password"` にはしない（パスワードとして保存・自動入力を持ちかけられるため）。
- **手順書**: ⓪-13 のN段階を次のとおりにした。⓪-15（U-1〜U-15。iPhone 16 Pro・iPad・Android・PC）を新設した。M-2 は「表示してからコピー」にした。
  - Android：QRを読む → ホーム画面のアプリを開き直す → 接続テスト。
  - iPhone・iPad：案D。
  - 予備：社内チャットの1対1・AirDrop。
- **操作ガイド**: 6ページ目を案Dの4ステップにした。ページ5の注記を「iPhone・iPad」にした。画面図の白地に白文字のボタンを直した。
- **印刷用PDF**: QR画像入りで作り直した。6ページで、`docs/qr/` の4枚と同じ 390×390 の画像が4枚入っている。gitには入れない。
- `docs/qr/README.md` のPDF作成コマンドを絶対パス（`$(pwd -W)`）に直した。相対パスでは Chrome が `docs` をホスト名と読んで失敗した。

## 却下した案とその理由
- **案A（アイコンを削除 → QRで設定 → ホーム画面に追加し直す）**
  - 再追加したアプリにSafari側の設定が引き継がれるかが不明。
  - 引き継がれても、商品マスタ（約4.9万件）とエラーの記録が消え、iPhone全台の再同期が同じ日に重なる（README 不具合ログ#4）。
  - 利用者の手順も多い。
- **案B（社内チャットの1対1・AirDrop）を主な方法にする**
  - トークン入りのリンクがチャットのサーバーに残り、削除できるかはサービス次第。
  - AirDropで受け取ったリンクは自動でSafariで開くことがあり、その場合はコピーできない。
  - 予備としてだけ残す。
- **案C（アプリのカメラで設定QRを読む）**
  - 2026-07-25 ごろ（操作ガイドにQR画像を入れたコミット `e8bc6bb` の頃）、同梱のZXingで4枚のQRの中身を確かめようとして読めなかった。BarcodeDetector も使えず、最終的に実機のカメラアプリで確認した。
  - 2026-10-21 の合成試験でも、ぼかしの無いまっすぐなQRが、1マス4画素以上だとほぼ読めなかった。
    - 1マス2〜3画素・半分に縮小・12°の傾きなら読める。
    - 読み取り器・二値化の方式・TRY_HARDER を変えても同じ。
    - 理由は特定できていない。
  - 作るには、複数の倍率で試す工夫と実機での計測が要り、工数とリスクが大きい。
  - 作る場合も、JANの読取（`scanner.js`）とは別の画面・別の読み取り器にする（README「将来拡張の設計メモ」）。
- **ボタンを Android にも出す** … Android はQRだけでホーム画面のアプリに入るので、不要な操作と、クリップボードにリンクを置く機会が増える。
- **UAの「iPad」だけで判定する** … iPadのSafariは既定でMacとして振る舞う（UAが Macintosh）ため、多くのiPadでボタンが出なくなる。
- **トークン欄を `type="password"` にする** … iPhone・ブラウザがパスワードとして保存・自動入力を持ちかけ、誤って保存される。
